# S1: frame bridge

Spike S1 from plan section 26, Phase 0. Lane: Engine and platform. It informs the
bridge design and contract 2, and gates Phase 2.

**Pass criteria (plan section 18, S1 gate).** At 4K 60 fps on the reference machine,
with main under load (autosave of the largest corpus project, agent tool traffic, a
50 ms long task every second, window resizes):

- p99 presentation jitter ≤ 4 ms and zero drops over 60 s;
- layer drag, 3D orbit, and walk pointer-to-pixel ≤ 33 ms at 60 Hz, and at most one
  frame worse than today;
- a ramp read back through `capturePage` matches, a 10-bit ramp shows no banding, and
  values above 1.0 survive on an HDR display.

**Result: fail.** The bridge works end to end. The Rust engine runs in a
`utilityProcess` and renders wgpu frames into IOSurfaces. Main verifies the engine's
one check-in and imports each surface once. The viewer draws the frames into a
WebGPU canvas. The bridge itself adds no measurable error: every drawn frame in every
playback run carried the right frame code (44,036 of 44,036). After tuning, main's
JavaScript adds 0.1 ms at p99. The image-quality lines pass.

Two of the three gate lines (playback and pointer-to-pixel) fail, for the three reasons
below. Each failure also appears in control runs that never read the engine's surface
(the viewer draws its own content on the same schedule). Each also applies to today's
in-renderer viewer.

1. **Jitter.** A canvas update reaches the display either one or two 120 Hz
   refreshes after its rAF, and runs switch between the two. This happens in every
   configuration, including an idle control with no bridge and no load. In the
   controls, Chromium's own stages take the same time either way, and the extra
   refresh appears after viz's swap. Each switch moves one frame by 8.33 ms, and 8 to
   31% of frame intervals have this error. Measured p99 jitter is 8.3 to 12.5 ms
   against a 4 ms target (24.5 ms in one run disturbed by another agent's GPU
   load).
2. **Drops.** Under the gate load, Chromium drops 2 to 5 already-drawn frames a
   minute (`STATE_DROPPED`) while main is blocked by an autosave that coincides with
   the long task. The control drops 5 per minute under the same load. With no load,
   drops are 0.
3. **Pointer-to-pixel under load.** p99 is 107 to 256 ms on every path, today's
   included. Input reaches the renderer through the browser main thread, and the load
   stalls that thread. Idle, the engine path runs about one 120 Hz refresh behind
   today at p50. Its p99 against the 33 ms target varies between runs with the
   compositor's pipeline depth: 26 to 138 ms.

**Recommendation:** keep the main path, as modified here: import once, send each pool
slot to the viewer once, and send per-frame descriptors from the engine directly to
the viewer. The B fallback inherits all three failures because it also presents
through Chromium. C′ (or A′) is the only option that presents outside Chromium's
compositor, so it is the only one that could fix the cadence line, and only if a
measurement shows that it does. Its frames still go through the macOS window server.
It could not fix input latency under main load.
Details are in [Recommendation](#recommendation).

Code: `engine/spikes/s1-bridge/` (its own Cargo workspace and a minimal Electron 44 app
that uses the Electron in `apps/desktop/node_modules`). Summaries of every run are in
`engine/spikes/s1-bridge/results/*.json`. Reproduce with the steps under
[Reproduce](#reproduce).

## What was built

### Engine (utility process): `crates/s1-engine`

- **Process and device.** `utilityProcess.fork` runs `app/engine-host.cjs`, which loads
  the napi-rs addon (`s1_engine.node`). The addon creates a wgpu 30 Metal device on the
  high-performance adapter.
- **Pool.** IOSurfaces are created with `IOSurfaceCreate` (`BGRA` or `RGhA` fourcc) and
  wrapped as `MTLTexture`s (`newTextureWithDescriptor:iosurface:plane:`). wgpu adopts
  them through `create_texture_from_hal`. A 4K pool of 14 uses 443 MiB in bgra and
  886 MiB in rgbaf16.
- **Render thread.** It renders a test pattern into the slot:
  - a 64-cell binary frame code (seq and revision);
  - a 0..1 ramp dithered with a 64 × 64 void-and-cluster blue-noise threshold on the
    8-bit path, and the same ramp undithered;
  - patches at 0.25 to 4.0;
  - a moving bar;
  - the dragged marker, which is the overlay geometry.

  Two extra full-screen ALU passes add about 6 ms of GPU work per frame as synthetic
  engine load. Orbit and walk render a 2,304-cube MSAA scene with depth.
- **Frame descriptors.** A descriptor is sent only after `device.poll` reports that the
  frame's command buffer is complete. It carries `{poolIndex, generation, seq, pts,
  duration, revision, inputTs, renderStart, gpuDone, colorSpace, flags,
  overlay[4]}`.
- **Playback.** It renders `leadFrames` ahead on a PTS grid locked to the display.
  Content frames last a whole number of refreshes (two at 120 Hz), and boundaries sit
  half a refresh before vsyncs.
- **Gestures.** Drag, orbit, and walk render once per new input revision.
- **Release.** A slot is reused only after the viewer returns `{poolIndex, seq}`.
  Mismatched releases are counted and ignored (0 in every run).

### Rendezvous and bridge (main): `crates/s1-mach`, `crates/s1-bridge`

1. Main makes a per-launch bootstrap name (`com.powermove.s1.bridge.` plus 128 random
   bits) and registers a receive right with `bootstrap_check_in`.
2. Main passes the name to the engine in `PM_S1_BRIDGE_NAME`.
3. Right after spawn, main records the engine's audit token (pid, pidversion), its
   parent pid, and its uid. It reads them through `task_name_for_pid` and
   `TASK_AUDIT_TOKEN`.
4. The engine looks the name up and sends one check-in. The message carries a send
   right to the engine's reply port and its claimed pid.
5. Main receives the check-in with the audit trailer (`MACH_RCV_TRAILER_AUDIT`) and
   verifies:
   - the claimed pid equals the token's pid;
   - pid and pidversion equal the spawn-time record;
   - the uid matches, and the parent is main;
   - the code signature satisfies `anchor apple generic and certificate
     leaf[subject.OU] = "<Team ID>"`.

   The signature check is bound to the audit token (`SecCodeCopyGuestWithAttributes`
   with `kSecGuestAttributeAudit`), so it checks exactly the instance that sent the
   message.
6. **Signature policy.** It comes from main's own signature. A signed main always
   requires its own Team ID. The unsigned development bypass is accepted only when
   main has no Team ID and `S1_ALLOW_UNSIGNED_DEV=1` is set. Electron's prebuilt
   binaries are only ad hoc signed, with no Team ID, so every Electron run here used
   the bypass, as its summaries record.
7. **On acceptance.** Main destroys the service right. That removes the name and
   discards anything still queued on it. Main then replies with a send right to a
   fresh anonymous port and arms a no-more-senders notification, so main learns when
   the engine exits or crashes.
8. **Later messages.** Every message on the anonymous port must carry the accepted
   audit token. Anything else is destroyed and reported. The engine accepts the reply
   only if it came from its parent.
9. **Surfaces.** Each pool surface goes to main once, as an `IOSurfaceCreateMachPort`
   send right. Main's native receive thread runs at user-interactive QoS. It looks
   each surface up, keeps a reference until `allReferencesReleased`, and hands the
   `IOSurfaceRef` pointer to JavaScript.
10. **Import.** Main calls `sharedTexture.importSharedTexture` once per surface.
11. **Wire parser.** It runs in main, so it is pure and total. A fuzz test feeds it
    random and mutated messages.

Rust tests (26, `cargo test --release`):

- **Rendezvous** (cross-process, with a peer binary playing the engine): a full
  session, the name is gone after one check-in, wrong pid, stale pidversion, non-child
  sender, an unsigned engine under a Team ID policy, and a crash after check-in
  reported as peer gone.
- **Signature checks:** a positive and a negative Team ID check against a real
  Developer ID process (Bun, Team 7FRXF46ZSN), Team ID syntax, and policy resolution.
- **Wire format:** round trips, rejections, and the parser fuzz.
- **Pool output:** frame code, ramp, and HDR patches read back from the IOSurface
  (both formats), and the dither's local-mean bound.
- **Other:** PTS grid retiming, blue-noise properties, and the camera.

### Viewer (renderer): `app/preload.cjs`, `app/viewer.js`

- `setSharedTextureReceiver` runs in the preload's isolated world. A sandboxed
  renderer with context isolation is enough.
- The preload calls `getVideoFrame()` and passes the `VideoFrame` to the main world
  through `contextBridge`, which carries `VideoFrame` objects natively. Isolated world
  to main world takes p99 0.1 ms.
- The main world draws each frame into a 3840 × 2160 WebGPU canvas. There are two draw
  paths:
  - `copyExternalImageToTexture` into an `rgba16float` texture, then a pass to the
    canvas;
  - `importExternalTexture`, sampled 1:1.

  The canvas is `bgra8unorm` for bgra pools. For rgbaf16 it is `rgba16float` with
  `toneMapping: 'extended'`.
- Each drawn frame's code is read back asynchronously and checked against its
  descriptor.
- After submitting, the viewer calls `VideoFrame.close()` and returns the slot when
  `queue.onSubmittedWorkDone()` resolves.
- Playback frames wait in a jitter buffer until their PTS. Gesture frames show on the
  next rAF.
- Input goes from the viewer to the engine over a `MessageChannelMain` port, never
  through main's JavaScript. With `rawInput`, pointer gestures use `pointerrawupdate`.

### Load on main (`app/load.cjs`)

- **Autosave, every 2 s.** `JSON.parse`, `structuredClone`, and `JSON.stringify` of a
  document, then an async write. This is the work `main/storage.ts` does for a store
  write. The document is a synthetic 884-layer project with 120 history entries
  (7.1 MB), which costs main 100 to 260 ms per autosave.
  - The private corpus stays off the repository. For scale, the largest project file
    on the reference machine is 1.4 MB, and its largest undo history is 60 MB on disk.
    History goes through the same main-thread store path.
  - A stress run uses a 56 MB document instead: 1.0 to 1.5 s of main work every 2 s.
- **Long task.** A 50 ms busy loop on main every second.
- **Agent traffic.** 20 tool calls a second: main to renderer (64 KB request), a
  600-layer reply, and JSON-RPC serialization in main. About 87 MB of replies a
  minute.
- **Resize.** A one-second interactive resize every 5 s at 60 `setBounds` a second.
- Every generator records what it actually did, and the summaries report it.

### Measurement

- **Clocks.** Presentation times come from Chromium's own frame reporting.
  `PipelineReporter` trace events start at a frame's BeginFrame (the rAF timestamp)
  and end at viz presentation feedback. Engine and main times use
  `CLOCK_UPTIME_RAW`. A ping-based offset maps them to the renderer, and a
  user-timing mark checks the mapping against the trace clock: the two agree within
  0.09 ms in every run.
- **Jitter.** For each content frame, presentation time minus PTS, minus the run's
  median. A frame counts as dropped if it was never drawn, drawn late, or not presented
  (its reporter state is not `PRESENTED`).
- **Cadence.** Each interval between consecutive presentations minus the content
  frame duration. An interval is irregular when it is more than half a refresh off.
- **Pointer-to-pixel** follows plan section 18. A native thread in main generates
  timestamped input at 120 Hz and injects it with `webContents.sendInputEvent`.
  Injected input queues behind a busy main thread, as OS input does. Each event's
  coordinates encode its sequence number, so coalesced events stay identifiable. The
  latency is from the generation timestamp to the presentation of the first drawn
  frame whose revision includes the event.
- **Today's path** (`baseline`): the renderer draws the dragged marker itself at the
  next rAF, which is what the current WebGL viewer does.
- **Window placement.** The window is shown without activation and moved off every
  screen. Two 15 s runs used a 160 × 90 pt window in the corner of the primary display
  to check off-screen presentation timing. The EDR check showed a 64 × 40 pt patch
  for 2 s.

Notes on the table:

- **Depth** is rAF to presentation in whole refreshes.
- **Off-screen versus on-screen.** The on-screen runs match the off-screen ones, so the
  off-screen window does not explain the results.
- **Run-to-run variation.** The two other runs without extra engine passes
  (`playback-bgra-load-light`, `playback-bgra-load-persistent-light`) show the same
  pattern. The second had 16 drops and 108 re-grids while another agent's GPU-heavy
  spike (`s4-render`) ran: its engine frames took 3.8 ms of GPU instead of about 1 ms.
- **Chromium feature flag.** `--enable-features=HarmonicFrameRate` changed nothing
  (`playback-bgra-idle-control-light-harmonic`).

**Where the jitter comes from.** Chromium's trace stages for each frame put the
variation after Chromium's own work.

- **Controls.** Every stage up to the swap takes the same time for frames presented one
  or two refreshes after their rAF. `StartDrawToSwapStart` has a median of 0.39 ms
  for depth-1 frames and 0.40 ms for depth-2 frames in
  `playback-bgra-idle-control-light`. Only swap end to presentation differs: 10.6 ms
  against 16.9 ms. Once viz has committed its Core Animation layer tree, macOS shows it
  on the next refresh or the one after.
- **Engine frames.** In the runs that draw engine frames, viz's draw also takes longer
  for depth-2 frames: 0.62 ms against 2.71 ms in `playback-bgra-load`, and 0.57 ms
  against 2.58 ms in `playback-bgra-load-persistent`. GPU work therefore raises the
  share of late refreshes.
- **Less GPU work** moves most frames to depth 1, but frames still switch. The idle,
  light control had 742 irregular intervals.
- **Redrawing every vsync** balances the two depths and lowers p99 offset jitter to
  4.51 ms, but the cadence errors stay: 863 irregular intervals. Redraw is not a fix.

Nothing on the engine or bridge side varies like this. Render, Mach send, forwarding,
the isolated-world hop, and the rAF all stay steady.

**Drops.** Every drop on the tuned path is `STATE_DROPPED`, meaning Chromium dropped a
frame the renderer had already drawn. Most come in pairs and triples during
main-thread stalls: the 50 ms long task, an autosave (100 to 260 ms), or both, often
during a resize. A few have no load event nearby, including one in an idle control
run. The control has the same count.

The per-frame transport, where main forwards every frame with `sendSharedTexture`,
also loses frames that arrive too late:

- Main's JavaScript delays forwarding by up to 153 ms, and the slack before PTS fell to
  6.4 ms.
- A deeper jitter buffer (lead 18 frames, pool 22, 696 MiB) removes the late arrivals,
  at 1.6 times the pool memory, but not the `STATE_DROPPED` ones.

In the 56 MB stress run, main is blocked for up to 1.5 s. During one stall that
overlapped a resize, the viewer drew nothing for about a second, so no slots came back
(1,629 waits for a free slot) and the engine skipped 45 frames. Main was not on the
frame path in that run.

**Display-link phase.** rAF timestamps jump by about half a refresh (4.1 to 4.2 ms)
after resizes and idle gaps. The first harness fitted a line through rAF times. Under
load, misindexed samples skewed the fitted period (8.319 ms instead of 8.333 ms), and
the PTS grid drifted until frames were drawn a refresh late: 99 late frames in one
minute.

The tuned viewer avoids this in four steps:

- it uses the display's nominal refresh period;
- it takes the phase from the median rAF offset;
- it switches to the newest 12 samples when they disagree by more than a quarter
  refresh;
- it decides at the rAF time plus a quarter refresh, which keeps a quarter refresh of
  margin through a jump.

After tuning, 0 frames were drawn late in every run except the stress run.

## Bridge API findings

These are the API facts plan section 18 asks S1 to confirm.

- **Import once.** `importSharedTexture` takes a median of 0.02 to 0.11 ms per 4K
  surface. The first call takes 0.23 to 0.42 ms. A Mach-received `IOSurfaceRef` pointer in
  `handle.ioSurface` works.
- **One import can be sent repeatedly.** In the per-frame runs, each of the 11 slots in
  rotation was sent with `sendSharedTexture` 334 to 337 times in 60 s. Every frame was
  received and every code checked: 3,595 to 3,601 frames per run, 0 receive errors.
  - A send resolves in 0.28 ms at p50, 7.3 ms at p99, and up to 108 to 191 ms when
    main is blocked.
  - Each send gives the renderer a new `SharedTextureImported`, which must be released.
- **One received import can make many frames.** The persistent transport sends each
  slot once (1.6 to 1.9 ms per send). The preload keeps that import and calls
  `getVideoFrame()` once per descriptor. 3,600 of 3,600 frames per run showed the new
  content.
  - The engine writes a slot only after the viewer's `onSubmittedWorkDone` for the
    previous use, so Chromium never reads a surface the engine is writing.
  - This uses Electron as documented, but the docs do not say that repeated
    `getVideoFrame()` calls see new IOSurface contents. An Electron upgrade test must
    cover it, which plan section 28 already requires for the bridge.
- **Release.**
  - Per frame, use `VideoFrame.close()` after submitting, then return the slot when
    `queue.onSubmittedWorkDone()` resolves. Submit to done takes 3.0 to 3.7 ms at p50
    and 8 to 13.7 ms at most.
  - Do not use the per-use release callback (`subtle.release(cb)`) to recycle a slot.
    It ran 0.3 ms after submit and before `onSubmittedWorkDone` in 3,601 of 3,601
    frames, 2.7 ms earlier at the median, so it does not signal that the GPU has
    finished reading.
  - Calling `subtle.release(cb)` directly also skips Electron's own notice to main.
    The preload must send it on Electron's internal channel
    (`IMPORT_SHARED_TEXTURE_RELEASE_RENDERER_TO_MAIN`), or `allReferencesReleased`
    never fires.
  - `allReferencesReleased` fired exactly once per surface at teardown (14 of 14, or
    22 of 22). Main then held 0 surfaces.
- **Receiver.** `setSharedTextureReceiver` in the sandboxed, context-isolated preload
  receives the texture, and `contextBridge` hands the `VideoFrame` to the main world.
- **Color space.** `colorSpace` passed at import reaches the `VideoFrame` for sRGB. The
  `srgb-hdr` transfer comes through as `null`, but the float values are intact.

## Recommendation

**Main path, as modified here (contract 2):**

1. Rendezvous as built: per-launch name, audit token with pidversion, Team ID
   signature check with the unsigned-only development bypass, and one check-in
   followed by deregistration.
2. Main imports each surface once and sends each slot once to each viewer receiver.
   It re-sends after a reload or popout. That path was not exercised here.
3. Per-frame descriptors go from the engine to the viewer over the `MessageChannelMain`
   port. Main's JavaScript leaves the per-frame path. That alone removed every late
   arrival under main load: 10 drops became 5, and the remaining drops are Chromium's
   own. Main still receives every descriptor over Mach for supervision.
4. Release on `onSubmittedWorkDone`, not on the per-use release callback.
5. Display timing: use the nominal refresh period, a median phase, phase-jump
   detection, and a quarter-refresh decision offset.
6. Formats: rgbaf16 is the only format that passes both the 10-bit line and the
   above-1.0 line. bgra with blue-noise dither passes the 10-bit line at half the
   memory. Use rgbaf16 on EDR displays and bgra with dither elsewhere or under memory
   pressure.
   - With main off the frame path, a lead of 10 frames is more than this path needed.
     Persistent runs never had less than 121 ms of slack before PTS. Shrinking the pool
     is the natural next tuning step. At lead 4, pool 8 is 253 MiB (bgra) or 506 MiB
     (rgbaf16).

**Gate decisions for Jude.** The jitter line, and drops under main load, fail for every
path that Chromium composites. That includes today's viewer and fallback B, so neither
can be fixed inside the bridge. Choose one:

- (a) Keep the main path and decide what to do about those two lines (a gate change is
  Jude's decision).
- (b) Build a C′ prototype for playback presentation only.
  - Gain: the engine presents a `CAMetalLayer` through `CAContext` and `CALayerHost`
    in main's window, timed with `presentDrawable:atTime:`, outside Chromium's
    compositor.
  - Costs: private API risk, and overlays and `capturePage` need their own layering.
  - Measure it with this harness before adopting it. The extra refresh measured here
    appears after Chromium's swap, and C′ frames also go through the window server.
  - Scrub, paused frames, and capture stay on the main path. C′ cannot fix input
    latency under main load either.

**Independent of the bridge:** move autosave serialization off main's thread.
Main-thread stalls are the cause of the remaining drops and of the input-latency p99
on every path.

B is not recommended. It presents through the same compositor and inherits all three
failures at lower resolution.

## Limitations

- **One machine.** Only the reference machine was measured. Base-machine gates are
  deferred (decision 11) and are unverified.
- **Shared machine.** Other agents' builds and GPU spikes ran during the measurements.
  Runs vary because of it (see the light runs above). Each summary records the
  machine's load.
- **Presentation feedback.** Presentation times are Chromium's presentation feedback,
  not optical measurements of the panel.
- **Refresh rate.** The display ran at 120 Hz, not the 60 Hz the gate names.
- **Window placement.** Most runs used an off-screen window. The two on-screen runs
  agree with them.
- **Gate load.** It uses a synthetic 7.1 MB document. The corpus's largest project stays
  private.
- **Signatures.** The Team ID path was verified in unit tests against a real Developer
  ID process. Electron runs used the unsigned development bypass (Electron's dist is ad
  hoc signed). A signed end-to-end
  run needs the release signing identity and was not done.
- **Not exercised:**
  - renderer reload, popout, and window-to-window moves (re-sending persistent
    imports);
  - engine crash and restart inside Electron (covered by the Rust peer-gone test);
  - DOM overlays drawn against `overlayGeometry`. The engine draws the marker, and the
    descriptor carries its rectangle.
- **C′ was not prototyped.**
