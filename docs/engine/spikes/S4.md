# S4: Text and vectors

Spike S4 from plan section 26, Phase 0. Lane: Text and vectors. The layout
half gates Phase 1 and the rendering half gates Phase 3a. Plan sections 10
and 12 apply.

**Pass criteria (plan):**

- Layout: identical line breaks, and advances within 0.25 px of today's
  layout, on the font corpus.
- Rendering: Vello coverage with float paint, `vello_gpu`, and Skia
  Graphite, each compared with CoreText, and a renderer chosen. Section 12
  sets the rendering bar at SSIM ≥ 0.98.

**Results**

| Part | Result |
|---|---|
| Level 1 layout vs today's Canvas2D | **Pass.** 5,110 of 5,110 corpus cases have identical line breaks. The largest advance error is 0.00101 px (p99 0.00024 px). |
| Native vs WASM layout | **Pass.** The output is byte-identical under JavaScriptCore (Bun) and V8 (Electron 44), using the metrics-and-shaping subsets. |
| Metrics-and-shaping subsets | **Pass, with a plan correction.** The section 12 table list is incomplete. It must add `maxp`, `feat`, `STAT`, and `ankr`; without `feat` and `STAT`, 216 corpus cases change. |
| Parley as the level 1 measurer | **Rejected by measurement.** 5,068 of 5,110 cases break identically and 3,433 are within 0.25 px. |
| Rendering vs CoreText (font smoothing on, the macOS look) | **Pass for outline text and paths, fail for bitmap emoji.** With the CoreGraphics profile, Vello scores ≥ 0.992 on every outline-text scene and ≥ 0.982 on every path scene (alpha SSIM over ink windows). Apple Color Emoji scores 0.559. |
| Rendering vs today's Canvas2D | **Partial.** With the Canvas2D profile, Vello reaches mean 0.979 and min 0.938 over ink windows; 15 of 21 scenes are ≥ 0.98. Over the full image, 20 of 21 scenes are ≥ 0.98. |
| 4K stress | Vello at 4K takes 3–7 ms per frame for caption-heavy scenes and 3 ms for 105k-element paths, measured on a loaded machine. |
| Renderer choice | **Vello (0.11, GPU compute, area coverage)** with an engine-owned stem-darkening profile. `vello_cpu` is the CPU fallback. The reasons are under [Choice](#choice). |

Code is in `engine/spikes/s4-text/`, which has its own Cargo workspace.

Reproduce:

- Layout half: `engine/spikes/s4-text/scripts/run-layout.sh`.
- Rendering half: `engine/spikes/s4-text/scripts/run-render.sh`.

Both scripts write to `engine/spikes/s4-text/out/`, which Git ignores; the
font blobs and system-font renders stay there. Results were measured on the
reference machine: M4 Max, macOS 27, Electron 44.0.0 (Chromium
152.0.7977.54), and Rust 1.96.1. Other spike lanes ran on the same machine
at the same time, with a load average of 7 to 8, so timings vary from run to
run (see the stress section).

## Layout half

### What was built

- **`s4-layout`.** The level 1 compatibility layout runs on HarfRust 0.14 and
  read-fonts 0.45. read-fonts provides the fontations metrics model that
  HarfRust 0.14 itself uses; Skrifa 0.48 provides outlines on the rendering
  side. The crate has these parts:
  - `legacy.rs`: a line-for-line port of `legacy/core/text-layout.ts`
    (`textSourceLines`, `glyphLayout`) and of raster.ts's caret boundaries.
    It keeps JavaScript's UTF-16 semantics: code-unit splits of long words,
    and lone surrogates. It also keeps the baseline at `size × 0.82` and the
    line height at `size × leading`.
  - `blink/`: a port of Blink's (Chromium 152) `measureText` path:
    - `PlainTextNode` word items and bidi runs;
    - `ShapeResult::ApplySpacing`, where letter spacing comes from tracking;
    - run segmentation (emoji presentation and script runs);
    - the `HarfBuzzShaper` font fallback loop;
    - Blink's glyph callbacks, shaped at Blink's 16.16 scale.
  - `canvas.rs`: the measuring context raster.ts builds:
    - the `fontStr(d)` family list, including the variable-font `FontFace`;
    - weight `d.weight || 500`;
    - italic.
  - `font.rs`: face facts and coordinates:
    - Blink's coordinates for installed fonts: `opsz` set to the size
      (CoreText optical sizing) and the hidden system font's own axes;
    - coordinates for `FontFace` web fonts (`custom_coords`);
    - CoreText-specific advances:
      - `trak` tracking;
      - `sbix` strike-sized color advances;
      - whole-unit `gvar` phantom-point advances;
      - HarfBuzz's rounded `HVAR` deltas.
  - `fallback_cache.rs`: Blink's ideograph fallback cache. It is stateful and
    depends on the order of earlier measurements.
  - `replay.rs`: answers registry queries from a recorded log. `subset.rs`
    builds the metrics-and-shaping subsets.
- **`s4-registry`.** The native font registry calls the same CoreText and
  AppKit APIs, in the same order, as Blink's macOS font matching
  (`font_matcher_mac.mm`, `font_cache_mac.mm`). It handles:
  - hidden system fonts (`System Font`, `system-ui`);
  - character fallback;
  - the last-resort font;
  - synthesized hyphens.

  Every answer is recorded, so the WASM side can answer the same queries
  from font bytes alone.
- **`s4-compare`.** Runs the corpus natively and compares every case with
  the Canvas2D capture (`--replay`, `--subsets`).
- **`s4-wasm`.** The replay layout as a `wasm32-unknown-unknown` module with
  a plain pointer-and-length ABI. It is 1.59 MB stripped (509 KB gzipped).
- **`capture/`.** A hidden Electron host that never shows a window and never
  takes focus. It measures the corpus with the legacy code itself:
  - `textSourceLines` and `glyphLayout` are imported from
    `legacy/core/text-layout.ts`;
  - variable fonts go through `typography/font-renderer.ts`;
  - `fontStr` is a verbatim copy of raster.ts's private helper.

  It also records the platform fonts Blink chose for each case, through the
  DevTools `CSS.getPlatformFontsForNode` command.

### Corpus

The corpus has 5,110 cases, generated by `capture/corpus.ts` from fonts that
ship with macOS only. It covers:

- 56 families, including SF Pro and the hidden system font (`System Font`,
  `system-ui`);
- weights 100 to 900, sizes 9 to 400, tracking from −10 to 40 px, and
  leading from 0.7 to 2.25;
- box widths, alignments, and whitespace;
- graphemes, UTF-16 splits, and lone surrogates;
- emoji: ZWJ sequences, flags, keycaps, and VS15/VS16;
- CJK (Simplified Chinese, Japanese, and Korean), Arabic, Hebrew,
  Devanagari, Thai, Syriac, Urdu Nastaliq, and astral CJK;
- variable fonts through the `FontFace` path: Skia (`gvar`-only), STIX Two,
  Kefa, Noto Sans Syriac, and SFNS with explicit axes.

Layout resolved 146 faces from 77 font files. Two captures are identical
apart from the random `FontFace` family names that `font-renderer.ts`
generates.

### Metrics-and-shaping subsets

Main serves these subsets to `pm-wasm` (section 12).

- **Size:** 133 faces, built from 589.1 MB of font files, produce 17.04 MB of
  subsets (2.89%). Building them takes 0.06 s.
- **Identity:** replaying the corpus over the subsets is bit-identical to
  the native CoreText run in all 5,110 cases, with 0 resolver misses.

**The section 12 table list needs four more tables.** The plan's list alone
changes 216 cases:

- **`feat`:** HarfBuzz and HarfRust map OpenType features to `morx`
  selectors only for feature types that `feat` lists. Without it, Helvetica
  Neue loses its ligatures and kerning: 192 cases change.
- **`STAT`:** HarfBuzz and HarfRust apply `trak` only to "modern" fonts, and
  they detect a modern font by the presence of `STAT`. Without it, SF Pro's
  tracking disappears: 24 cases change.
- **`ankr`:** anchor points for `kerx` format 4 attachment.
- **`maxp`:** the glyph count that every metrics table is sized by.

Two more parts are needed:

- **`HVAR` for `gvar`-only fonts.** These fonts get a synthesized `HVAR`
  (`subset.rs`, one region per `gvar` tuple). A unit test checks every Skia
  glyph across a 7 × 5 axis grid; the worst difference is under 1/1024
  unit.
- **Facts about dropped tables.** Layout needs some facts about tables the
  subset drops: whether `sbix` or another color table is present, and
  whether advances come from phantom points. These facts travel with the
  registry answers (`FaceFacts`), not in the subset.

### Native vs WASM

`scripts/wasm-identity.mjs` loads the module, feeds it the subsets, the
recorded registry answers, and the corpus, and compares the output JSON byte
for byte with the native run over the same inputs. It also compares the
output value for value with the native CoreText run.

| Runtime | Output bytes identical | Cases identical to CoreText run | Layout time |
|---|---|---:|---:|
| Bun 1.3.14 (JavaScriptCore) | yes | 5,110 / 5,110 | 5.6 s |
| Node 24.18.1 in Electron 44.0.0 (V8 15.2) | yes | 5,110 / 5,110 | 5.9 s |

The layout uses no transcendental math. Every value comes from integer
16.16 shaping or from f32/f64 arithmetic and rounding, which WASM defines
identically.

### Parley

The plan names Parley for layout, so Parley was measured as the level 1
measurer. `s4-parley` runs the same `legacy` wrapping port, with
`measureText` widths taken from a Parley 0.12 layout configured the way the
engine would configure it:

- fontique's system collection and fallback;
- the `fontStr(d)` family list;
- weight, italic, size, and letter spacing;
- explicit axes, with `opsz` set to the size;
- `FontFace` fonts registered from the same files.

| Measurer | Identical breaks | Within 0.25 px |
|---|---:|---:|
| Blink port on HarfRust (this spike) | 5,110 | 5,110 |
| Parley 0.12 | 5,068 | 3,433 |

Of Parley's 1,677 failures:

- 1,212 are the kerning string (`AVATAR Tower WAVE…`): Parley kerns and
  tracks AAT and SF fonts differently from Blink.
- The rest are concentrated in SF Pro, the hidden system font, and Avenir
  Next. Parley does not reproduce CoreText's `trak`, its optical sizing, or
  Blink's font matching.
- CJK, emoji, and math fallback choices also differ.

So level 1 measuring stays on the Blink port over HarfRust. Parley fits
level 2, which is planned to use grapheme-aware breaking and font metrics
rather than today's wrapping.

## Rendering half

### What was built

`s4-render` builds 32 scenes, all drawn on transparent targets, so the alpha
of white content is its coverage:

- 15 text scenes:
  - SF Pro at 9–18, 20–40, 64–144, and 400 px;
  - 10 families at 14 and 48 px, and SF weights 100–900;
  - New York, italics, and tracking;
  - CJK, Arabic, Hebrew, Devanagari, and Thai;
  - emoji;
  - caption strokes.
- 6 path scenes:
  - filled and stroked rectangles, rounded rectangles, ellipses, the 0.46
    star, and polygons;
  - hairlines;
  - a 72-spoke Siemens star;
  - a 400-cubic blob;
  - an even-odd heptagram;
  - tiny circles.
- 11 fit scenes, at 9–144 px in four families.
- 3 stress scenes at 3840 × 2160.

Glyph positions come from the level 1 layout (the Blink port on the CoreText
registry). They match Canvas2D advances within 0.001 px, so each comparison
isolates rasterization.

The same scenes are drawn by these renderers:

| Renderer | Version and configuration |
|---|---|
| CoreText (reference) | `CTFontDrawGlyphs` and CoreGraphics into a 32-bit float premultiplied sRGB bitmap. Subpixel positioning, no quantization, font smoothing off (`coretext`) and on (`coretext-smooth`). |
| Canvas2D (today) | The hidden Electron host with `capture/render.ts`. Text is drawn the way raster.ts `rasterText` draws it (`fillText` per line); caption strokes are drawn the way `captions/render.ts` draws them. Paths use `Path2D`. GPU-accelerated 2D canvas; Electron reports `skia_graphite: enabled_on`. |
| Vello | `vello` 0.11, GPU compute on wgpu 30 Metal, `AaConfig::Area`. |
| `vello_gpu` | 0.3. Strips are prepared on the CPU; coverage and paint are done on the GPU. |
| `vello_cpu` | 0.3, with 4 threads. |
| Skia Graphite | skia-safe 0.153.3 (prebuilt `graphite-metal` binaries), Metal, `RGBAF16` (half-float) surface. Typefaces load from the same bytes through the CoreText font manager. |

Two numbers are reported for every scene:

- **Alpha SSIM:** Wang et al. 2004, with an 11 × 11 Gaussian and σ = 1.5.
  The full-image mean is reported alongside a mean over ink windows (local
  mean coverage > 1/512). The ink-window number is the strict one, because
  empty background cannot inflate it.
- **Ink ratio:** Σα(test) / Σα(reference).

Review sheets for Jude stack one row per renderer:
`out/render/<scene>.png`. Rows top to bottom are:

### The macOS look is CoreText with font smoothing

Today's Canvas2D text tracks CoreText *with* font smoothing:

| Comparison | Ink ratio |
|---|---|
| Canvas2D vs CoreText with smoothing | 0.995–1.006 |
| Canvas2D vs plain CoreText | 1.24 (Canvas2D is heavier) |

CoreGraphics smoothing is a dilation:

- It adds 38% ink at 12–24 px, 18% at 48 px, and 9% at 96 px.
- The extra ink is asymmetric: the glyph centroid moves up 0.29–0.30 px from
  24 px up (measured by `coretext::positioning`).
- A probe confirms that CoreText positions glyphs continuously, without
  quantization, in both axes.

Plain outline coverage therefore cannot match either target:

| Renderer | vs CoreText with smoothing | vs Canvas2D |
|---|---|---|
| Plain Vello, text scenes | mean 0.824, ink ratio 0.81 | mean 0.810 |

A coverage gamma alone does not close the gap: the best γ reaches only mean
0.913 against CoreText with smoothing and mean 0.877 against Canvas2D.

### Stem darkening

`s4-render fit` sweeps two engine-side parameters on the fit scenes:

- an outline expansion of 0–0.5 px per side, through each renderer's
  `font_embolden` (`kurbo::expand_path`);
- a vertical ink offset.

It fits them against both references and produces two profiles
(`vello_r::Tune`). Bitmap glyphs are never expanded. Stroke passes only snap
glyph positions.

| Profile | Expansion per side | Offset | Positions | Target |
|---|---|---|---|---|
| CoreGraphics | min(0.0175 × size, 0.34) px | up by min(expansion, 0.30) px | exact | CoreText with font smoothing |
| Canvas2D | min(0.11 + 0.0075 × size, 0.46) px; none above 256 px (Skia draws those as paths) | up by min(0.65 × expansion, 0.30) px | x to 1/4 px, y rounded (Skia's subpixel positioning) | today's Canvas2D |

The fit was done on the fit scenes; the scene table below is held-out
validation.

| Fit scenes (11 sizes × 4 families) | Plain | Tuned |
|---|---|---|
| Vello vs CoreText with smoothing (CoreGraphics profile) | 0.778–0.869 | min 0.994, mean 0.995 |
| Vello vs Canvas2D (Canvas2D profile) | 0.605–0.866 | min 0.967, mean 0.984 |

Findings:

- **Against CoreText with smoothing (the plan's 0.98 gate),** Vello with the
  CoreGraphics profile passes 20 of 21 scenes:
  - outline text min 0.992 and paths min 0.982;
  - the one failure is emoji.
- **Emoji (Apple Color Emoji, `sbix` bitmaps).** CoreText's own
  `CTFontDrawGlyphs` (and Skia, which rasterizes through CoreText) draws the
  bitmaps 6.0 px higher at 48 px than Canvas2D does. Vello's placement
  agrees with Canvas2D:

  | Renderer | Ink centroid y (px) |
  |---|---:|
  | CoreText, Skia | 20.69 |
  | Canvas2D | 26.67 |
  | Vello, Canvas2D profile | 26.67 |
  | Vello, `vello_gpu`, `vello_cpu`, plain | 27.0 |

  Level 1 must match Canvas2D, so this is a reference-side difference, not
  a Vello defect. It still fails a literal "SSIM vs CoreText" gate, and that
  gate needs an emoji rule from Jude (see open items).
- **Against today's Canvas2D,** the Canvas2D profile reaches mean 0.979.
  Six scenes fall below 0.98 over ink windows:
  - caption strokes, 0.959;
  - small SF semibold, 0.947;
  - small families, 0.956;
  - small SF, 0.975;
  - emoji, 0.938;
  - tiny circles, 0.980.

  The remaining gap is small text. Chromium draws CoreText's own smoothed
  glyph masks at quarter-pixel phases; outline expansion approximates that
  dilation but not its exact per-stem shape.
- **Skia Graphite.**
  - It reproduces Canvas2D paths exactly (1.000), because it is Chromium's
    path code, and small text at 0.987–0.992.
  - It diverges on larger text (0.886–0.976) and on emoji (0.539).
  - Against CoreText with smoothing it scores 0.78–0.95 on text, because
    Skia's CoreText masks are lighter (ink ratio 0.93).
  - The `RGBAF16` half-float surface rendered and read back correctly.
- **"Coverage with float paint."** Vello 0.11 and `vello_gpu` 0.3 accept
  only `Rgba8Unorm` targets (`render_to_texture` and `RenderTargetConfig`).
  `vello_cpu` writes an RGBA8 `Pixmap`. The workable form is to render
  coverage, as white or a mask, to 8-bit (step 1/255), then paint and
  composite in float in the engine's own pass. Every number above measures
  that coverage.
- **`vello_gpu` glyph atlas.** It is faster for fill-only text (2.9 ms vs
  10.3 ms on the subtitles stress scene), but it caches coverage at
  quantized phases: 8 of 21 scenes stay ≥ 0.98, and small text drops to
  0.78–0.87. Bitmap glyphs in `vello_gpu` must go through the atlas, because
  direct bitmap paints panic with "pixmap image sources are not supported
  by Vello GPU".

### 4K stress

- **Captions:** 24 blocks of two-line, 72 px bold captions with a 6 px stroke
  over a translucent rounded box; 2,212 glyphs.

- **Paths:** a 100,000-segment stroked spiral, a 4,000-cubic blob, and a

## Choice

**Vello 0.11** (GPU compute, area coverage) renders text and vectors, with
the stem-darkening and positioning profile owned by the engine:

- `compat` level 1 uses the Canvas2D profile.
- Level 2 uses the CoreGraphics profile.
- **`vello_cpu`** is the CPU fallback (section 26's failure path). Its
  coverage matches `vello_gpu` to three decimals, so the same profiles
  apply.

Reasons:

1. **Quality.** It is the only renderer that reaches ≥ 0.99 against the macOS
   look on every outline-text scene, given the CoreGraphics profile. Skia
   Graphite cannot get there: its glyph masks come from CoreText's scaler
   with Skia's own contrast handling (ink ratio 0.93), and the engine cannot
   tune them.
2. **Speed.** It is fast across the board at 4K: 3–7 ms on caption-heavy
   frames and paths, with sub-millisecond CPU encode. Strokes stay on the
   GPU. `vello_gpu` is 10–20× slower on stroked captions and large paths.
3. **Determinism and portability.** Coverage comes from Skrifa outlines,
   not from the platform scaler, so the CLI, the headless hosts, the WASM
   web player (decision 8), and a later Windows port all render the same
   text. The Skia route ties pixels to CoreText on macOS and FreeType
   elsewhere. It also adds a large C++ dependency, and its first frame takes
   150–310 ms.
4. **What Skia does better.** Skia is faster in steady state (2–6 ms) and
   pixel-identical to today's Canvas2D paths. That second advantage matters
   only for level 1 shapes, and Vello already reaches 0.980–0.997 there.

What the choice costs:

- Vello targets are 8-bit. Float paint is the engine's own pass over
  coverage.
- Vello has no glyph-coverage atlas, so very dense static text re-rasterizes
  every frame. That still costs 3–4 ms for 5,544 glyphs at 4K.

## Open items and plan feedback

1. **Section 12 table list.** It should add `maxp`, `feat`, `STAT`, and
   `ankr`, and state that `HVAR` is synthesized for `gvar`-only fonts. I did
   not edit the plan; that needs an RFC or Jude.
2. **The rendering gate is ambiguous.** "SSIM ≥ 0.98 vs CoreText" and
   "level 1 matches today" have different targets. Today's Canvas2D itself
   scores only 0.828–0.977 against CoreText with smoothing on text scenes.
   Proposal:
   - Level 2 is gated against CoreText with smoothing. It passes for outline
     text and paths.
   - Level 1 is gated against Canvas2D. It currently reaches mean 0.979, min
     0.938, and fails at 0.98 on six scenes.

   The plan's fallback is to keep legacy shims longer for level 1 text.
   Before that, the next step is to fit per-stem masks or a coverage curve
   on top of the expansion, for sizes ≤ 18 px and stroked captions.
3. **Emoji.** Level 1 matches Canvas2D (0.938) and fails against CoreText
   (0.559), because CoreText's own `sbix` placement sits 6 px higher at
   48 px. The gate should name Canvas2D placement as correct for `sbix`
   bitmaps.
4. **Not measured here:**
   - typing latency (a section 12 gate, Phase 3c);
   - Jude's side-by-side review (the sheets are in `out/render/`);
   - SVG text through usvg;
   - 3D Text;
   - `compat` level 2 layout;
   - synthetic bold and italic faces in rendering. No render scene used one
     (`syntheticFaces` is empty); Vello would need `font_embolden` and a
     skew to match CoreText's synthesis.
5. **Layout scope.** Level 1 covers what raster.ts measures: plain text
   layers and the glyph units animators use. Caption layout
   (`captions/render.ts` word layout) uses the same measuring context and
   is not separately ported here.
