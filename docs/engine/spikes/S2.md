# S2: precision and encode

Spike S2 from plan section 26, Phase 0. Lane: Color. It informs contract 4 (the color
contract) and decision 15, and gates Phase 2.

**Pass criteria (plan).** On a prototype: the pipeline transparency and codec
generation bars of section 2; the VideoToolbox formats; f16 versus f32 on 12-bit and
16-bit sources; the bit depth of HEVC with alpha; AVAssetWriter tags; the tags that
make QuickTime match the viewer; Metal precise math; `rgba32float` filtering and
blending on every reference machine.

**Result: measured in full on the reference machine; partial pass.** Pipeline
transparency passes. Codec generation passes for ProRes when the encoder input is
`v216` or `y416`. As written, it fails for ProRes 4444 with alpha (2 CV next to
α = 0) and for H.264 (the max-CV clause). Every other item is measured, and the
results lead to plan corrections: the ProRes 422 decode format, the H.264
generation bar, the transparency bar's clipping, and the dither clause.

| Item | Result |
|---|---|
| Pipeline transparency (ProRes 4444 XQ → `y416`, ProRes 422 HQ → `x422`, f32) | **Pass**, exact at 16 bits on every sample when output clipping is off. With section 9's clipping on, the only differences are source samples outside the codable range, which match the clipped reference exactly. |
| Codec generation, ProRes | **Pass for 4444 and for 422 through a `v216` encoder input** (0 CV, 0.000 dB). **Fail for 422 through `x422`** (8 CV). **Fail by 1 CV for 4444 with alpha**: up to 2 CV, all within 16 px of an α = 0 pixel. PSNR within 0.1 dB in every ProRes case. |
| Codec generation, H.264 | **Max-CV clause fails** (216 CV; Apple's own VideoToolbox re-encode of the same frames differs from Apple's preset by 164 CV). PSNR: Y′ −0.14 dB, Y′CbCr +1.59 dB versus Apple at a matched data rate. |
| f16 versus f32 | f32 exact on every 10-, 12-, and 16-bit source. f16 is not: up to 3 CV at 12-bit, and 16-bit ramps keep 7,169 to 13,558 of 65,536 levels. |
| HEVC with alpha | Alpha is 8-bit in every profile. Main10 and 4:2:2 alpha streams encode correctly but **play back corrupted through AVFoundation on macOS 27**. Ship 8-bit (Main), as the plan says. |
| AVAssetWriter tags | `colr` (`nclc` in MOV, `nclx` with the range flag in MP4), `gama`, H.264 VUI, and 24000 timescales verified on disk. AVAssetWriter's default 600 timescale stores 23.976 fps as 24.000 fps. |
| QuickTime and Safari tags | **1-13-1 passes** (max ΔE2000 0.063 ProRes, 0.158 HEVC 10-bit, 0.718 H.264 8-bit). 1-2-1 with gamma 2.2 fails (max 1.98 to 2.01). |
| Metal precise math | Available through wgpu MSL passthrough. Not needed for any bar: naga's fast-math output is exact for transparency and for E round trips at 12 and 16 bits. |
| `rgba32float` | Filterable, blendable, multisample, and storage on the M4 Max, with wgpu granting `FLOAT32_FILTERABLE` and `FLOAT32_BLENDABLE`. Bilinear weights have 8 fractional bits on both float formats. |
| Dither (section 17) | Passes the bit-depth bar's dither clause. Values already on the output grid stay unchanged. Output is deterministic and seeded per frame, and alpha is never dithered. The clause does not tell dithered from undithered output (see the dither section). |

Reference machine only (decision 11): Apple M4 Max MacBook Pro, 128 GB, built-in XDR
display, macOS 27.0 (26A428), Metal 4, SDK 27.0, Rust 1.96.1 (`engine/env.sh`), wgpu
30.0.1, objc2 0.6 and objc2 framework crates 0.3.2. Base-machine `rgba32float` and
hardware ProRes results are **unverified**: the base M1 has no ProRes engine, and
section 13 expects software ProRes decode there.

Code: `engine/spikes/s2-precision/` (its own Cargo workspace). See
[Reproduce](#reproduce).

## What was built

The spike is a Rust prototype of the section 17 pipeline, built on objc2
VideoToolbox, CoreVideo, CoreMedia, AVFoundation, Metal, and wgpu:

- **Test material** (`material.rs`). It is made with AVAssetWriter and
  VideoToolbox, never `prores_ks`. Synthetic 1920×1080 frames contain luma ramps
  with chroma gradients, uniform Y′CbCr noise across the codable range (superwhites,
  sub-blacks, out-of-gamut RGB), 75% bars, and super-black and super-white patches.
  These are written as ProRes 4444 XQ (opaque, and with a 16-bit alpha ramp),
  ProRes 422 HQ, HEVC Main10, and H.264. A second "natural" set has 48 frames: a
  moving hue field, a zone plate, three soft-edged moving discs, bars, a grey ramp,
  and a radial alpha. It is written as ProRes 422 HQ, 4444 XQ, and 4444 XQ with
  alpha.
- **Decode** (`vt.rs`). VTDecompressionSession decodes to a requested
  pixel format, or to the decoder's native format, with IOSurface-backed,
  Metal-compatible buffers.
- **Import** (`gpu.rs`). `CVMetalTextureCache` creates an `MTLTexture` per
  plane with no copies. wgpu wraps it through `create_texture_from_hal`: `y416` as
  one `RGBA16Unorm` texture, and `x422` and `x420` as `R16Unorm` plus `RG16Unorm`.
- **Source pass** (`pipeline.wgsl`). It applies section 13's normalization
  (for `y416`, Y′ = (v − 4096) / 56064, C = (v − 32768) / 57344, A = v / 65535;
  `x422` and `x420` use c = v / 64), the Rec.709 matrix, and premultiplication. In
  Standard, the result is in E. With linear blending on, it is E⁻¹ (the extended
  sRGB curve), giving `rgba16float` or `rgba32float` working storage.
- **Encoder-input pass**. This pass unpremultiplies (guarded), converts back to E,
  applies the matrix, and writes codes. It optionally clips to section 9's codable
  range and applies blue-noise RPDF dither. Chroma follows section 9: 4:2:2 uses
  co-sited point decimation, and 4:2:0 uses type 0 siting with a declared filter
  (point decimation horizontally, a two-tap average vertically). The pass writes
  directly into the IOSurface of the CVPixelBuffer that VideoToolbox encodes. It
  outputs `y416`, `x422`, `v216`, `x420`, `420v`, and `l64r`.
- **Test sinks**. Raw `y416`, `x422`, and `v216` buffers are written to disk and
  read back identically (`pixbuf::write_raw_sink`).
- **Encode and mux**. VTCompressionSession encodes, with properties set before
  the first frame. AVAssetWriter muxes the compressed samples (pass-through), with
  movie and media timescales set from the frame rate.
- **Experiments**, one module each, each writing JSON to
  `target/s2-work/results/`: `formats`, `transparency`, `precision`, `generation`,
  `tags`, `quicktime`, `encoders`, `dither`, `math`, `caps`.

## VideoToolbox formats and normalization

`formats.json`. Each source was decoded to `y416`, `x422`, `x420`, `xf20`, `420v`,
`420f`, `RGhA`, `l64r`, `b64a`, and `BGRA`.

- **All 50 codec and format pairs decode.** The sources were ProRes 4444 XQ (with
  and without alpha), ProRes 422 HQ, HEVC Main10, and H.264. Every pair reports the
  hardware decoder, except ProRes to `b64a` (no hardware flag reported).
- **ProRes decodes above 12 bits.** On the ProRes 4444 XQ material, only 31% of
  `y416` luma samples have their low 4 bits zero, so the decoder delivers 16-bit
  values. The value is not a 12-bit code shifted up. The transparency bar's "exact at
  12-bit" is therefore a weaker claim than what the prototype achieves, which is
  exact at 16 bits.
- **ProRes 422 also decodes above 10 bits.** Apple's own ProRes 422 tracks declare
  `BitsPerComponent = 12`. `x422` truncates that to 10 bits, while `v216` (16-bit
  4:2:2, packed Cb Y0 Cr Y1) keeps it. The codec generation results show this
  matters.
- **Encoder native inputs**, read from each VTCompressionSession pixel buffer pool:

  | Codec and profile | Native input |
  |---|---|
  | ProRes 422 Proxy, 422 HQ | `sv22` (undocumented) |
  | ProRes 4444, 4444 XQ | `s4as` (undocumented) |
  | HEVC Main, Main10, Main42210 | `420v`, `x420`, `x422` |
  | H.264 | `420v` |
  | HEVC with alpha: Main, Main10, Main42210, Main44410 | `v0a8`, `x0a8`, `x2a8`, `x4a8` |

  `v0a8` is public: 8-bit 4:2:0 plus an 8-bit alpha plane. `x0a8`, `x2a8`, and
  `x4a8` have no public CoreVideo constant. They hold 10-bit 4:2:0, 4:2:2, or 4:4:4
  luma and chroma as MSB-aligned u16 samples, plus an 8-bit alpha plane.
- **Encoder list** (`VTCopyVideoEncoderList`, 27 entries): software and
  `AppleProResHW` encoders for every ProRes flavor, plus hardware and software
  H.264 and HEVC. The HEVC-with-alpha (`muxa`) encoder runs in hardware (its
  ProfileLevel list includes Main, Main10, Main42210, Main444, and Main44410) and in
  software (Main and Main10 only).

## Codec generation

`generation.json`. The source is the natural material (48 frames). Apple's path is
`AVAssetExportSession` with the preset named in each row. The engine's path is VT
decode, then the engine (f32, no effects), then the encoder input, then
VTCompressionSession, then AVAssetWriter. Both outputs are decoded by VideoToolbox
and compared at 10 bits, and at the native depth where it differs.

| Case | Max CV, engine vs Apple (10-bit) | Native | PSNR Δ Y′CbCr (Y′) | Bar |
|---|---|---|---|---|
| ProRes 422 HQ → ProRes 422 (`apcn`), encoder input `v216` | 0 | 0 | 0.000 (0.000) dB | **Pass** |
| ProRes 422 HQ → ProRes 422, encoder input `x422` | 8 | 8 | +0.29 (+0.26) dB vs the decode, −0.26 dB vs the original frames | **Fail** (max CV) |
| ProRes 4444 XQ → ProRes 4444 (`ap4h`) | 0 | 0 at 12-bit | 0.000 dB | **Pass** |
| ProRes 4444 XQ with alpha → ProRes 4444 | 2 | 9 at 12-bit | −0.007 (+0.001) dB | **Fail** by 1 CV |
| ProRes 422 HQ → H.264 1920×1080 preset | 216 | — | +1.59 (−0.14) dB | **Fail** (max CV); Y′ PSNR −0.14 dB is outside 0.1 dB |

Controls in every row:

- **Engine repeat.** Two engine exports decode identically (0 CV).
- **Encoder input.** When the encoder input format equals the decode format, it is
  bit-identical to the decode.
- **Direct.** VideoToolbox encoding the decoded buffers with no engine in the path.

Findings:

1. **Apple's ProRes path keeps 16 bits.** `apple_path_probe` re-encodes VT decodes
   in nine formats. Only `y416` and `v216` reproduce Apple's preset exactly. `v210`
   reproduces the `x422` result (8 CV). `2vuy`, `b64a`, `l64r`, `RGhA`, and `BGRA`
   differ by 12 to 120 CV, and `r4fl` fails to decode (−12905). The engine's
   ProRes 422 encoder input must be `v216`, not `x422`, and ProRes 422 should decode
   to `v216` (or `y416`) when it feeds an export.
2. **4444 with alpha.** All differences lie within 16 px of an α = 0 pixel. They are
   90,199 samples at a 1 px radius and 0 at 16, 64, and 128 px. Apple's export
   carries the source's straight color under α = 0. The premultiplied engine writes
   zero there, and ProRes's 8×8 DCT blocks carry that difference into neighboring
   visible pixels by up to 2 CV. PSNR is unaffected (−0.007 dB), and alpha is exact
   (0 CV).
3. **H.264.** The engine is High profile with Rec.709 tags. The average bit rate
   was searched to 7,958,302 bps, the plateau that gives 3.30 Mbps against Apple's
   3.34 Mbps. Apple's preset converts the 4:2:2 source to 4:2:0 itself, and its
   chroma is 2.7 to 2.9 dB worse than the engine's declared filter. The direct control
   shows that VideoToolbox re-encoding Apple's own decoded frames differs from the
   preset by 164 CV. A max-CV bar between two runs of a long-GOP lossy encoder with
   different rate control cannot be met. Engine Y′ PSNR is 0.14 dB below Apple at a
   1.4% lower data rate.

## f16 versus f32 working storage

`precision.json`: exhaustive synthetic sources through the source and output passes.
Errors are in source code values.

| Source | f32 Standard | f32 linear | f16 Standard | f16 linear |
|---|---|---|---|---|
| `y416` 12-bit luma ramp (4,096 codes) | exact | exact | max 3, 44% wrong, 2,983 levels kept | max 1, 18%, 3,727 levels |
| `y416` 12-bit random Y′CbCr (1M px) | exact | exact | max 3, 40% | max 1, 8.8% |
| `y416` 16-bit luma ramp (65,536) | exact | exact | max 55, 9,663 levels | max 24, 13,558 levels |
| `y416` 16-bit alpha ramp | exact | exact | max 32, 7,169 levels | max 32, 7,169 levels |
| 16-bit RGBA grey ramp at 16-bit | exact | exact | max 32, 7,169 levels | max 21, 10,674 levels |
| the same, read at 12-bit | exact | exact | max 2, 50% | max 2, 32% |
| the same, read at 10-bit | exact | exact | max 1, 25% | max 1, 8% |
| the same, read at 8-bit | exact | exact | max 1, 6.2% | max 1, 2.1% |
| 16-bit color over an alpha ramp (α ≥ 16/65535), at 10-bit | exact | exact | max 1, 25% | max 1, 11% |
| `x422` 10-bit luma ramp (1,024 codes) | exact | exact | max 1, 3.3%, 1,010 levels | exact |

- f16 has an 11-bit significand, so near 1.0 its step is 2⁻¹¹ (about 0.43 10-bit
  CV). A matrix round trip adds rounding, so 10-bit content flips by 1 CV on a few
  percent of samples in Standard, while linear storage is exact for 10-bit 4:2:2.
- 8-bit sources survive f16: k/255 stored in f16 is within 0.06 CV.
- f16 cannot hold 12-bit or 16-bit sources or alpha. The plan's rule ("exports
  default to 32-bit when the output or any source exceeds 10 bits") is confirmed
  and necessary.

## HEVC with alpha

`encoders.json`. The test frames are an alpha ramp (1,920 columns, 65,536 levels)
over grey, and an opaque grey ramp. They go through the engine to a straight `y416`
encoder input and then to `kCMVideoCodecType_HEVCWithAlpha`. Each stream is decoded
to the decoder's native format, and its planes are read directly.

| Settings | Base layer (`hvcC`) | Native decode | Alpha bits, levels | Luma levels (of expected) | Luma max error, 10-bit CV |
|---|---|---|---|---|---|
| default | Main, 4:2:0, 8-bit | `v0a8` | 8, 255 | 219 of 220 | 6 (one 8-bit code) |
| Main10 | Main10, 4:2:0, 10-bit, `lhvC` | `x0a8` | 8, 255 | 821 of 877 | 2 |
| Main10, Quality 1.0, TargetQualityForAlpha 1.0 | Main10 | `x0a8` | 8, 256 | 877 of 877 | 1 |
| Main42210 | RExt, 4:2:2, 10-bit | `x2a8` | 8, 255 | 821 | 2 |
| Main44410 | RExt, 4:4:4, 10-bit | `x4a8` | 8, 255 | 821 | 2 |
| `OutputBitDepth 10` without a Main10 profile | — | — | encode error −12902 | — | — |

- **The alpha plane is 8-bit in every profile and decoder output format.** Main10
  raises only the color layer to 10 bits.
- **Main10 and 4:2:2 alpha do not play back correctly on macOS 27.** The decoder's
  native planes are correct (2 CV against the analytic ramp). VideoToolbox's
  converter out of `x0a8` and `x2a8` is wrong: VTPixelTransferSession to `y416`,
  `x420`, `420v`, or `RGhA` gives luma errors of up to 955 CV on synthetic content
  with known codes. Requesting `y416` from the decoder gives 930 CV. The same
  happens on playback: AVPlayerItemVideoOutput frames of the Main10 and Main42210
  files score 4.3 to 4.7 dB premultiplied-RGB PSNR, against 41 to 49 dB for the
  others. `x4a8` (Main44410) and `v0a8` convert correctly, within the target format's rounding.
  - CoreVideo's description of `x0a8` declares 16 bits per block for the luma
    plane, but its black block is 5 bytes (`0x1004010040`, four packed 10-bit
    values of 64). The converter probably reads the layout as packed while the codec
    writes u16. `examples/probe_x0a8.rs` shows raw samples.
  - Conversions into `x0a8`, `x2a8`, and `x4a8` from `y416` are off by up to 3 luma
    CV and 2 chroma CV. Conversion into `v0a8` is exact.
- **Quality against AVFoundation's preset**
  (`AVAssetExportPresetHEVCHighestQualityWithAlpha`, which writes 8-bit Main) on
  the natural 4444 XQ alpha material, from native planes:

  | Encode | Alpha PSNR (8-bit) | Y′CbCr PSNR (10-bit) | Data rate | Playback premultiplied RGB PSNR |
  |---|---|---|---|---|
  | Apple preset | 55.22 dB | 47.73 dB | 3.27 Mbps | 41.45 dB |
  | Engine, Main (default) | 55.22 dB | 47.54 dB | 3.05 Mbps | 41.29 dB |
  | Engine, Main10 | 55.22 dB | 49.06 dB | 1.81 Mbps | 4.46 dB (corrupt) |
  | Engine, Main42210 | 55.22 dB | 54.37 dB | 2.20 Mbps | 4.65 dB (corrupt) |
  | Engine, Main44410 | 55.22 dB | 55.82 dB | 2.36 Mbps | 48.59 dB |

  The Alpha bar ("HEVC alpha PSNR at least that of AVFoundation's preset") passes
  at equality. The alpha encoder output is identical across profiles at default
  quality.
- **Tags.** HEVC with alpha does not copy the input buffers' color attachments
  into the format description. The engine must set ColorPrimaries,
  TransferFunction, and YCbCrMatrix as session properties, or the file is untagged.

## AVAssetWriter tags

`tags.json`. ProRes 422 HQ (MOV), H.264 (MOV and MP4), and HEVC Main10 (MOV and MP4)
were each encoded with four tag sets. Sample entries, `colr`, `gama`, `fiel`,
`chrm`, `stts`, `mvhd`, `mdhd`, and the H.264 SPS VUI were parsed from disk.

- **MOV** writes `colr` `nclc` (no range flag). **MP4** writes `colr` `nclx`
  with `full_range = 0`, plus `fiel` and `chrm`.
- **1-13-1** writes transfer 13 in `colr` and in the H.264 VUI (1, 13, 1), and reads
  back as `IEC_sRGB`.
- **1-2-1 + gamma 2.2** writes transfer 2 and a `gama` box (2.19999695). It reads back
  as `UseGamma` with `GammaLevel` 2.2.
- **No transfer function** still writes `colr` with transfer 2 (unspecified), and
  the VUI as (1, 2, 1).
- **Timescales.** With `movieTimeScale` and `mediaTimeScale` set, 23.976 fps is
  stored as `stts` 1001 at timescale 24000. With AVAssetWriter's defaults, it is
  stored as 25 at timescale 600, which is 24.000 fps. Section 17's timescale rule is
  required, not cosmetic. The spike's AVFoundation-written source material itself
  has 600-timescale frame times, which is why its frame 2 sits at 2000/24000.
- **Gap:** the HEVC VUI is not parsed. The H.264 VUI and `colr` agree in every case.

## QuickTime and Safari tags (bar 3)

`quicktime.json`. A 40-patch chart is used: 24 ColorChecker patches, a 10-step grey
scale, and primaries and secondaries at 255. The chart goes through the engine
encoder input, VideoToolbox, and AVAssetWriter with each tag set. AVPlayer and
AVPlayerItemVideoOutput then deliver frame 2 as `RGhA` or `BGRA`. That frame's
attached CGColorSpace is converted to the display profile with ColorSync. The viewer
side converts the sRGB codes to the same profile. Both are compared by CIEDE2000 on
64×64 patch-center means. The main display (built-in XDR, "Color LCD") and
Display P3 targets give the same results.

| Tags | ProRes 422 HQ, `RGhA` | H.264 MP4, `RGhA` | HEVC 10-bit MP4, `RGhA` | `BGRA` output, worst |
|---|---|---|---|---|
| 1-1-1 (broadcast) | 4.30 max / 2.15 mean | 4.68 / 2.29 | 4.37 / 2.17 | 4.62 |
| **1-13-1** | **0.063 / 0.010** | **0.718 / 0.230** | **0.158 / 0.053** | 1.22 (H.264) |
| 1-2-1 + gamma 2.2 | 1.98 / 0.53 | 2.00 / 0.65 | 2.01 / 0.55 | 2.38 |
| no transfer | 4.30 / 2.15 (treated as 1-1-1, HDTV profile) | 4.68 | 4.37 | 4.62 |

- **"Rec.709 (QuickTime and Safari)" should be 1-13-1.** It passes bar 3 (max 1.0)
  in every codec through `RGhA`. The 8-bit `BGRA` delivery of an 8-bit H.264 adds
  rounding (max 1.22). The bar is defined on the display conversion, so the engine
  measures with a float output.
- Gamma 2.2 misses at mid greys (worst on grey 24 and 32). 1-1-1 and untagged files
  are treated as HDTV (BT.709 OETF inverse), as expected, and look darker by design.
- **Gap:** Safari and the QuickTime Player app were not driven directly. Both use
  this AVFoundation and ColorSync path, but a Safari check needs a browser window on
  Jude's screen.

## Metal precise math through wgpu

`math.json`. Six functions were dispatched over an f32 sweep, compared with f64 in
ULP. The E round trips cover every 16-bit and 12-bit code.

| Variant | pow(x, 1/2.4) | pow(x, 2.4) | E | E⁻¹ | E round trip 16-bit and 12-bit |
|---|---|---|---|---|---|
| WGSL via naga (wgpu's default options = fast math) | 9.09 ULP | 26.7 | 11.3 | 12.8 | 0 and 0 failures |
| MSL passthrough, `metal::precise::` | 2.75 | 14.8 | 3.52 | 9.21 | 0 and 0 |
| naga MSL rewritten to `precise::`, via passthrough | 2.75 | 14.8 | 3.52 | 9.21 | 0 and 0 |
| Offline metallib, `-fno-fast-math` | 2.75 | 14.8 | 3.52 | 9.90 | 0 and 0 |
| `#pragma METAL fp math_mode(safe)`, `-fmetal-math-mode=safe`, `fast::` | same as fast | | | | 0 and 0 |

- wgpu-hal 30.0.1 compiles naga output and passthrough MSL with
  `MTLCompileOptions::new()` (fast math). There is no option to change that.
- **Precise math is available** (`PASSTHROUGH_SHADERS` is granted) by calling
  `metal::precise::` functions or by rewriting naga's MSL. The `safe` math mode
  pragma and flag do not change these functions on this compiler.
- **It is not needed for the bars measured here**: transparency is exact, and E round
  trips have zero failures with fast math. Keep naga's default output. Use
  passthrough with `precise::` only for a kernel whose bar requires better than about
  12 ULP in pow, exp, or log.

## `rgba32float` on the M4 Max

`caps.json`.

- **Reported support.** Metal reports `supports32BitFloatFiltering` and
  `supports32BitMSAA`, plus the Apple9 and Metal3 families. wgpu grants
  `FLOAT32_FILTERABLE`, `FLOAT32_BLENDABLE`, `TEXTURE_FORMAT_16BIT_NORM`,
  `TEXTURE_ADAPTER_SPECIFIC_FORMAT_FEATURES`, and `PASSTHROUGH_SHADERS`.
  `Rgba32Float` has FILTERABLE, BLENDABLE, MULTISAMPLE x2 and x4, RESOLVE, and
  storage read and write.
- **Filtering.** The midpoint of 1.0 and 1 + 2⁻²⁰ filters to exactly 1 + 2⁻²¹, so
  the filtered arithmetic is f32. Bilinear weights, however, have 257 distinct
  values (8 fractional bits, maximum weight error 2⁻⁹), and `rgba16float` is the
  same. Hardware filtering is not a precise resampler on either format. Export
  resampling (Lanczos) should use `textureLoad` taps with weights computed in the
  shader.
- **Blending.** Additive blending keeps 1 + 2⁻²² exactly. Source-over with
  24-bit-significand values is within 1 ULP of CPU f32.

| 0.40 → 0.42 | `420v` | on | 0.317 | 0.009 | 91 |
| 0.40 → 0.42 | `x420` 10-bit | off | 0.429 | 0.429 | 110 |
| 0.40 → 0.42 | `x420` | on (opt-in) | 0.351 | 0.009 | 53 |

- **On-grid values.** Every 8-bit code from 16 to 235 and every 10-bit code from 64
  to 940, set exactly through `y416`, is unchanged with dither on over 4 frames.
  Neutral chroma stays exactly neutral.
- **Determinism.** Two renders of a frame are byte-identical. Frames 0 and 1 differ
  on 34% of luma samples.
- **Alpha.** No alpha sample changes in `y416` or `l64r` output.
- **Bar wording.** The clause "with default dither on an 8-bit output, the
  16-column local mean is within 0.5 CV of ideal" is met by undithered rounding
  too: a window mean of rounded values is never more than 0.5 CV from the ideal. A
  test that separates dithered from banded output is the column mean over at least
  64 rows within 0.05 CV, measured on a shallow ramp. Dithered output gives 0.009;
  undithered gives 0.48.

## Recommendations

### Contract 4 (color)

1. **Decode formats** (amends section 13).
   - ProRes 4444 and 4444 XQ decode to `y416`.
   - ProRes 422 decodes to `v216` (or `y416`), not `x422`, whenever the frame can
     reach an export. `x422` keeps only 10 bits of a 12-bit-plus decode, and
     re-encoding from it costs up to 8 CV against Apple's own path.
   - `x422` stays acceptable for preview.
   - `v216` imports as one `RGBA16Unorm` texture (Cb, Y0, Cr, Y1). The prototype's
     `fs_from_v216` shows the source pass.
2. **Encoder inputs.**
   - ProRes 422 family: `v216`.
   - ProRes 4444 family: `y416`.
   - HEVC Main10: `x420`, or `x422` for 4:2:2.
   - H.264 and HEVC Main: `420v`.
   - HEVC with alpha: `y416` straight, which VideoToolbox converts exactly to `v0a8`.
     A direct engine-written `v0a8` is better if the engine is to own the 4:2:0
     filter (section 9).
   - Never feed `x0a8` or `x2a8` through VideoToolbox's converter.
3. **Normalization constants.** The `y416` and `x422`/`x420` normalization in
   section 13, and the matrix, are exact at f32 on every code. Keep them as written.
4. **Clipping.** Keep clipping at output to the codable range. Section 25's
   transparency test should compare against the reference clipped to the same range.
5. **Precision defaults.**
   - `rgba16float` is adequate for 8-bit sources and for preview.
   - It is not exact for any 10-bit Y′CbCr source in Standard (up to 1 CV on 1.8 to
     3.3% of samples), nor for 12-bit or 16-bit sources (up to 3 CV at 12-bit).
   - Keep the rule "exports default to 32-bit when the output or any source exceeds
     10 bits".
   - Treat 16-bit surfaces (Blender, 16-bit PNG and TIFF) as sources exceeding 10
     bits.
   - Section 2's bars that say "at 32-bit precision" are the right scope.
6. **Alpha.**
   - Premultiplied working values lose color under α = 0. A straight-alpha ProRes
     4444 export therefore differs from Apple's by up to 2 CV near transparent
     edges.
   - Either state that the Alpha and Codec generation bars exclude pixels within 16
     px of α = 0, or add a "color under zero alpha" pass-through for unmodified
     straight sources.
   - The measurements support the first. The second needs a second working plane.
7. **Output tags.**
   - "Rec.709 (QuickTime and Safari)" is **1-13-1** (limited range).
   - Write tags as VTCompressionSession properties for every codec, not only as
     buffer attachments: HEVC with alpha drops attachments.
   - Set `movieTimeScale` and `mediaTimeScale` explicitly.
8. **Dither.** The section 17 design is implemented as specified and behaves as
   specified. Tighten the bit-depth bar's dither clause as described above.
9. **Math.** Fast math (naga default) is sufficient for the color invariants.
   Record the passthrough `precise::` route in contract 4 as the escape hatch.
10. **Cache keys.** Precision and dither seed (frame index) both change output
    bytes. Both must be cache-key components, as contract 4 lists.

### Decision 15 (Blender surfaces: 16-bit PNG through AgX)

16-bit PNG is the right surface format. A 16-bit RGBA ramp through the engine at
f32 keeps all 65,536 levels exactly, at 16, 12, 10, and 8 bits, in Standard and
linear. At f16 it keeps 7,169 levels (10,674 in linear), with errors up to 32/65535,
and 1 CV at 10-bit on 25% of samples.

Two consequences follow:

- A project with Blender layers should count as having a source above 10 bits and
  export at 32-bit by default.
- The surface's straight alpha at 16 bits survives f32 exactly, but not f16 (max 32
  of 65,535).

There is no reason to move to EXR or 32-bit float surfaces for SDR AgX output.

### Plan corrections for section 2 and section 17

- **Codec generation.** For H.264, replace the max-CV clause with PSNR within 0.1 dB
  (Y′ and Y′CbCr) at a matched data rate, or compare against a VideoToolbox encode
  of the same encoder input. A long-GOP encoder versus AVAssetExportSession cannot
  meet 1 CV: the direct control misses by 164 CV.
- **HEVC with alpha.** Keep it at 8-bit. 10-bit alpha streams are produced
  correctly but are not viewable through AVFoundation on macOS 27. Re-test on each
  macOS major release.
- **Bit-depth bar.** Revise the dither clause (see Dither).

## Gaps

- **Reference machine only** (decision 11). M1 and base Air `rgba32float` and
  ProRes results are unverified. On those machines the plan's per-machine fallback
  ("drop unsupported 32-bit features per machine") is untested.
- **Safari and QuickTime Player** were not driven directly. Bar 3 is measured as
  defined, through AVPlayerItemVideoOutput and ColorSync.
- **HEVC VUI** colour description is not parsed. The `colr` box and the read-back
  extensions are.
- **The H.264 generation case** uses Apple's 1920×1080 preset only. The engine
  would offer quality tiers, which are not compared.
- **The `x0a8` diagnosis** rests on CoreVideo's description and observed behavior.
  No Apple documentation exists for `x0a8`, `x2a8`, or `x4a8`.
- **Decode timings** in `formats.json` are single-run, cold, and include the
  buffer pool. They are not a performance measurement.

## Reproduce

```sh
cd engine/spikes/s2-precision
source ../../env.sh
cargo build --release --all-targets
RUST_TEST_THREADS=4 cargo test --release          # unit tests and the GPU round-trip test
./target/release/s2-precision all                 # about 2 minutes once the material exists; results in target/s2-work/results/
./target/release/s2-precision <experiment>        # material, formats, transparency, precision,
                                                  # generation, tags, quicktime, encoders, dither, math, caps
```

The `math` experiment's offline-metallib variants need `xcrun metal` (Xcode). The
`quicktime` and `encoders` experiments use AVPlayer offscreen and open no windows.
Diagnostics: `examples/probe_x0a8.rs` (raw `x0a8` planes against an `x420` decode),
`examples/probe_alpha10.rs` (converter output per format), `examples/probe_v216.rs`,
and `examples/probe_gen.rs`.
