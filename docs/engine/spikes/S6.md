# S6: decode

Spike S6 from plan section 26, Phase 0. Lane: Media. It informs `pm-media`
and gates Phase 2.

**Pass criteria (plan):** the corpus decodes into wgpu without copies, and
random access is exact, including on coarse timebases. The Seeking bar
(section 2) defines exact: for every supported codec, random access to frame N
equals sequential decode of frame N. That includes open-GOP HEVC, B-pyramid
H.264, edit lists, interlaced MXF, and 1 ms WebM, 90 kHz TS, and 1/600 MOV at
23.976 and 29.97. Frame N is picked with the section 5 rule 7 selection.

**Result: pass on the measured corpus, with two engine requirements found on
the way.** The corpus is 11 e2e fixture videos plus 25 generated files.

- Every file decodes on every backend that applies to it.
- Every composition frame of every file was fetched by random access in a
  shuffled order, twice: once with a new decoder per seek and once within one
  session. Each fetched frame equals the sequential decode of the frame rule 7
  selects (MD5 of the visible planes, framemd5 layout). That is 5,806 probes
  per pass over 62 backend and file pairs, with 0 mismatches.
- Every file reaches wgpu through at least one backend whose textures alias the
  decoder's output memory: 0 CPU copies.
- Sequential decodes match FFmpeg's framemd5. There are two exceptions, both
  explained below. On the edit-list file FFmpeg presents one frame fewer, and
  the other 92 match. FFmpeg cannot output `v0a8`, so VideoToolbox's HEVC
  alpha decode is checked against AVFoundation and FFmpeg's own HEVC alpha
  decode instead. MOV and MP4 files also match AVFoundation's `AVAssetReader`
  frame for frame.

The two requirements:

1. **VideoToolbox sessions need an end-of-sequence sample before a seek.**
   VideoToolbox has no reference-flush call. When a reused session seeks to an
   open-GOP H.264 random-access point, it builds reference lists from stale
   pictures: 35 of 150 seeks on `h264-opengop.mov` were wrong without it, and
   0 with it.
2. **FFmpeg `get_buffer2` must give every plane its own buffer reference.**
   FFmpeg 8.1's HEVC alpha path otherwise frees a frame under a live decode.
   Before the fix, 6 of 12 runs on `hevc-alpha.mov` with frame threading had
   corrupted random-access frames.

Both are fixed in the spike and covered by tests. Interlaced MXF is not in the
corpus (see Gaps).

Code: `engine/spikes/s6-decode/` (its own Cargo workspace). Reproduce: see
the end of this report. All numbers come from Jude's M4 Max (decision 11) on
macOS 27.0 (26A428), with Homebrew FFmpeg 8.1.2, dav1d 1.5.4, and libvpx
1.16.0, measured on 2026-10-11 while other worker lanes shared the machine.

## What was built

- **Frame index** (`src/index/`), from container tables. Nothing is decoded,
  and payloads are read only where the container has no table.
  - **MOV and MP4:** `stts`, `ctts`, `stss`, `stsz`, `stsc`, `stco`/`co64`,
    and `elst`, with QuickTime edit-list semantics: samples decoded but not
    presented are marked, and so are partly covered first frames.
  - **Matroska and WebM:** Cues for keyframes, plus a scan of block headers
    only for per-frame timestamps, because Cues index only keyframes.
    BlockAdditional (alpha) locations are recorded. Every Cue point matched a
    scanned keyframe.
  - **MPEG-TS:** no tables exist, so FFmpeg's demuxer scans the packets
    without decoding (`DemuxScan`). This is the only scanned format.
  - **H.264 and HEVC:** the first VCL NAL type of each sample comes from a few
    header bytes per sample, so open-GOP sync samples are marked: HEVC CRA and
    BLA, and H.264 non-IDR I pictures. RASL pictures and H.264 leading
    pictures are marked too. A decode plan for frame N starts at the last sync
    sample whose PTS is not after N. It skips the leading pictures of an open
    sync sample.
  - **Cross-check:** every index is checked against FFmpeg's demuxer (packet
    count, presented PTS, keyframe flags).
  - **Build time:** 0.03 to 1.9 ms per file for the small corpus and 6.7 ms
    for the 4K HEVC file (`stbl` parse plus NAL headers).
- **Exact time** (`src/time.rs`). All in i128:
  - the nominal rate from section 13 probe item 5;
  - rule 7 selection, with q being the stream timebase capped at a quarter of
    the nominal frame duration;
  - the composition grid, so the expected source frame of every composition
    frame is known independently of rule 7.
- **VideoToolbox** (`src/vt.rs`).
  - The format description comes from the sample entry's child atoms, as
    AVFoundation does, or from Matroska CodecPrivate.
  - Output formats follow section 13:
    - ProRes 422 → `x422`;
    - ProRes 4444 and XQ → `y416`;
    - 10-bit H.264 and HEVC → `x420` or `x422`;
    - 8-bit → `420v` or `420f`;
    - HEVC with alpha → `v0a8`.
  - Range comes from the bitstream. The output buffer's format and attachments
    are checked against the request: every buffer matched.
  - AV1 decodes in hardware on the M4 Max (`av01` → `420v` or `x420`).
- **FFmpeg** (`src/ff.rs`): `ffmpeg-sys-the-third` 5.0 linked to Homebrew's
  dylibs. It provides probing, the TS demux, and decode with a custom
  `get_buffer2` that hands decoders Metal-shared memory.
- **Direct software sessions** (`src/sw/`):
  - **dav1d,** with its picture allocator pointed at the pool.
  - **libvpx VP9,** with external frame buffers in the pool, for alpha.
  - **A paired native decoder:** two FFmpeg native VP8 or VP9 decoders (color
    and BlockAdditional alpha) that both render into the pool.

  These exist because FFmpeg's `libdav1d`, `libvpx-vp9`, and `libvpx` (VP8)
  wrappers decode into their own memory, so through FFmpeg those frames need
  a copy.
- **Zero-copy import** (`src/gpu.rs`, `src/pool.rs`).
  - **VideoToolbox:** `CVPixelBuffer` planes come in through
    `CVMetalTextureCache` as per-plane `R8`/`RG8` or `R16Unorm`/`RG16Unorm`
    textures. `y416` comes in as one `RGBA16Unorm` texture, and the AYCbCr
    order is handled in the shader. Every texture's IOSurface is checked to be
    the buffer's IOSurface.
  - **Software:** decoders write into page-aligned slots, each wrapped once
    with `newBufferWithBytesNoCopy` (shared storage). Each plane is a linear
    `MTLTexture` over that buffer, at the exact address the decoder reported
    for the plane, and this is checked per frame.
  - **Into wgpu:** both kinds are wrapped through
    `wgpu_hal::metal::Device::texture_from_raw` and `create_texture_from_hal`
    (wgpu 30).
- **Section 13 normalization** (`src/normalize.wgsl`): a compute pass to
  Y′, Cb, Cr, and A in `rgba32float`, with the plan's constants:

  | Format | Code value c | Y′ | C | A |
  |---|---|---|---|---|
  | `x420`, `x422` | v / 64 | (c − 64) / 876 | (c − 512) / 896 | – |
  | `y416` | v | (v − 4096) / 56064 | (v − 32768) / 57344 | v / 65535 |
  | FFmpeg LSB n-bit | v | (c − 16·2ⁿ⁻⁸) / (219·2ⁿ⁻⁸) | (c − 128·2ⁿ⁻⁸) / (224·2ⁿ⁻⁸) | v / (2ⁿ − 1) |

  Full range uses 2ⁿ − 1 with chroma centered at 2ⁿ⁻¹. Each frame's GPU
  output is compared with a CPU reference computed in f64 and rounded to f32.
  The two agree within 1 ULP everywhere (maximum |d| 1.2e-7). VideoToolbox
  and FFmpeg decodes of the same file produce bit-identical normalized f32
  output on every file where both apply.
- **Matrix runner** (`src/run.rs`, `src/bin/s6.rs`), cargo tests
  (`tests/matrix.rs`), the corpus generator (`scripts/gen-corpus.sh`), an
  AVFoundation framemd5 tool (`scripts/avf-framemd5.swift`), and a summary
  generator (`scripts/summary.py`).

### Coarse timebases and rule 7

On 1 ms, 1/600, and 90 kHz timestamps, rule 7 selected the expected source
frame for every composition frame, with 0 mismatches. The naive rule (last
frame with PTS ≤ t) picked the wrong frame 70 to 75 times out of 150 on 1 ms
WebM, 1/600 H.264, and 90 kHz TS at 23.976. It also failed 40 and 50 times out
of 100 on 1/600 ProRes, and 20 of 60 on the fixture WebMs.

The `time.rs` unit tests check rule 7 for both NTSC rates at all three
timebases over 20,000 frames: 0 mismatches.

Random access on these files was exact on every backend.

### Edit lists

`editlist-trim.mov` starts mid-GOP and partway through a frame
(`media_time` 41002 at 1/30000).

- The index presents 93 frames (131 samples decoded), with QuickTime
  semantics. AVFoundation agrees on all 93.
- FFmpeg's MOV demuxer presents 92 frames: it drops the partly covered first
  frame. The other 92 match exactly, offset by one.
- The composition grid has one hole after that first frame, which rule 7
  holds correctly.

## Finding 1: VideoToolbox seeks within a session

A VideoToolbox session that has decoded pictures elsewhere keeps its H.264
short-term references across a non-IDR I picture. An open-GOP seek in a reused
session therefore builds reference lists from stale pictures. On
`h264-opengop.mov` this gave 115 of 150 frames correct: 31 mismatched, 4
missing, and 69 frame errors. With a new session per seek, 150 of 150 were
correct. HEVC passed either way, because a CRA's reference picture set is
explicit.

Fixes tried:

- **An end-of-sequence NAL unit prepended to the next sample:** no effect.
- **An end-of-sequence NAL unit (H.264 type 10, HEVC type 36) submitted as its
  own sample before the seek:** works, 150 of 150. VideoToolbox reports that
  sample as bad data (−12909) through the callback. The spike tags it with
  `sourceFrameRefCon` and drops it.

`VtDecoder::start_sequence` does this on every seek. `S6_NO_EOS=1` reproduces
the failure.

This matters for the decode service, because reusing a session is most of the
seek cost:

| | New session | Same session |
|---|---|---|
| ProRes (small) | about 25 ms | 0.2 ms |
| ProRes, 4K | 27.7 ms | 1.24 ms |
| H.264 and HEVC (small) | 6 to 9 ms | 1.5 to 3 ms |
| HEVC Main10, 4K | 48.6 ms | 18.8 ms |

Session creation dominates (about 24 ms for ProRes), so sessions must be
pooled and reused across seeks, as section 13's decode service already says.
Every reused-session seek needs the end-of-sequence sample.

## Finding 2: FFmpeg 8.1 HEVC alpha frees planes it still writes

FFmpeg 8.1 decodes HEVC with an alpha layer to `yuva420p`. It calls
`get_buffer2` for both layers. Then `replace_alpha_plane` (`hevc/refs.c`)
replaces the alpha-layer picture's buffer reference that contains `data[0]`
with the base picture's alpha-plane buffer. It keeps decoding the alpha
layer's other planes.

FFmpeg's default allocator gives every plane its own buffer, so those planes
stay alive. A `get_buffer2` that puts all planes in one reference is allowed
by the API, but with it this frees the whole allocation under a live decode.
The alpha layer's chroma writes (value 128) then land in whichever frame
reuses the memory.

The spike's original allocator did exactly that. Random-access frames on
`hevc-alpha.mov` had small blocks of neutral chroma (8 to 112 chroma
samples per frame) in 6 of 12 runs with 4 threads, and in none of 12 runs
with 1 thread. The sequential pass and the
FFmpeg CLI always matched.

The fix: `get_buffer2` creates one `AVBufferRef` per plane, each holding the
pool slot, and adoption finds each plane's slot by address. The regression
test (10 runs, both random-access passes) fails on the old code and passes now.

This applies to `pm-media`'s production allocator. It should be reported
upstream.

## Finding 3: the plan's nominal-rate rule is ambiguous on coarse timebases

Section 13 item 5 picks "the supported rate whose frame duration is within ±1
timebase unit of the median duration". At 1 ms, both 24 and 23.976 qualify
(41.667 and 41.708 ms), and so do 30 and 29.97. At 1/600, 24 and 23.976
(25.0 and 25.025 units) qualify. So do fine timebases where the two rates differ by at most one unit per
frame: 30 and 29.97 at 1/15360, and the NTSC rates and their integer
neighbors at 1/24000 and 1/30000 (1001 against 1000 units).

The spike breaks ties with the mean duration over the same 300-frame window.
That chose the right rate on every file. Without a tie-break the rule has no
single answer for most real files.

**Plan correction (section 13 item 5):** "if several supported rates qualify,
the one closest to the mean duration over the same window."

## Other observations

- **H.264 4:2:2 10-bit decodes through VideoToolbox on the M4 Max.** The
  session reports `UsingHardwareAcceleratedVideoDecoder = true`, the output is
  `x422`, and it matches AVFoundation and FFmpeg exactly. Section 13's
  hardware note says "H.264 4:2:2 10-bit is software-only". The property alone
  does not prove that the media engine did the work: VideoToolbox ran at
  7,611 fps, and FFmpeg at 11,323 fps on 4 threads, at 320×180. The routing
  decision should be measured on 4K camera files before Phase 3b. Base
  machines are unverified (decision 11).
- **AV1:** hardware VideoToolbox decode works on the M4 Max (M3 and later, as
  the plan says). dav1d is the zero-copy fallback.
- **`hevc-alpha.mov` (e2e fixture) is untagged** but was encoded with BT.709
  coefficients. Section 9 decodes untagged video at heights up to 576 as
  BT.601, so its green reads (0.08, 1.18, 0.03). Decoded as BT.709 it is
  within 0.004. The decode itself is exact: VideoToolbox, AVFoundation, and
  FFmpeg agree. This is a fixture tagging issue. The content checks name it
  as a known exception. Every other fixture color check is within 0.004,
  except green on `vp8-opus.webm` (0.019, from lossy VP8; the check's
  tolerance is 0.06).
- **Import cost:** creating the per-frame texture costs a median of 3 to 27 µs
  across all formats, 4K included. Normalization plus readback, which only
  the spike needs, is 0.3 to 1.7 ms small and 7.7 to 8.6 ms at 4K (median).
- **Software threading:** at 4K, FFmpeg's HEVC decoder seeks in 117 ms against
  48.6 ms for VideoToolbox (new session), and decodes at 119 fps against
  704 fps.

## Gaps

- **Not in this corpus:** interlaced MXF, MXF index tables, and field-order
  handling (all named in the Seeking bar). Also DNxHD and DNxHR, CineForm,
  MJPEG, DV, DPX, AVI, WMV, FLV, MPEG-PS and M2V, M2TS and MTS, 3GP, OGV, VOB,
  and image sequences. None of these were generated or tested: Homebrew's
  FFmpeg can encode most of them, but the lane's time went to the two
  findings. The index has no MXF parser.
- **FFmpeg build:** the spike links Homebrew FFmpeg 8.1.2, which is a GPL
  build with nonfree-capable configuration, not decision 12's LGPL-only
  build. The decoders exercised (`h264`, `hevc`, `vp8`, `vp9`) are LGPL, and
  dav1d and libvpx are BSD-licensed, so the results should transfer, but they
  were not rerun on our build.
- **Machines:** M4 Max only. Base machines are deferred (decision 11): base M1
  has no ProRes engine, and M1 and M2 have no AV1 hardware decode.
- **Session limits:** hardware session limits, arbitration by main, and
  read-ahead scheduling (the decode service) were not exercised. Each run used
  at most two sessions at a time.
- **Probe:** the probe beyond the frame index is not built. That includes
  section 13 probe items 1, 2, 4 (priming), 6, and 7, and color metadata
  beyond range and matrix.
- **Not compared against VideoToolbox:** `y416` and `x422` buffers are
  checked against AVFoundation, but the pipeline-transparency bar (exact
  12-bit equality through the engine) belongs to S2.
- **Normalization exactness:** GPU normalization equals the f64 CPU reference
  rounded to f32 within 1 ULP, not bit for bit. Metal's division is not
  correctly rounded. This is far below a code value (1/65535 is about 1.5e-5)
  and is S2's concern under precise math.

## Reproduce

```sh
source engine/env.sh
cd engine/spikes/s6-decode
scripts/gen-corpus.sh                       # seek corpus into corpus/ (gitignored)
cargo build --release
target/release/s6 --threads 4 --json fixtures.json ../../../apps/desktop/e2e/fixtures
target/release/s6 --threads 4 --json corpus.json corpus
python3 -I scripts/summary.py fixtures.json corpus.json
cargo test --release -- --include-ignored --test-threads=1   # gate as tests
```

Useful environment variables:

- `S6_TRACE=1`: per-probe packet and frame traces.
- `S6_NO_EOS=1`: reproduces finding 1.
- `S6_DEFAULT_GET_BUFFER=1`: FFmpeg's own allocator, which copies.
- `S6_LOG_GET_FORMAT=1`: logs the formats FFmpeg offers.
