## Crash: exact reason and root cause

A screen-free Objective-C probe reproduced:

```text
CAMetalLayerInvalidOperation: -nextDrawable should not be called when using CAMetalDisplayLink.
```

The probe creates a valid 64×64 CAMetalLayer with a Metal device, initializes
CAMetalDisplayLink with that layer, pauses the link, and calls nextDrawable inside
an Objective-C exception handler. The exception occurs even when the link is
paused and has never been added to a run loop. Visibility and positive size alone
therefore cannot fix this crash.

P-120's renderer stored only an optional callback drawable. If none was supplied,
`draw` called `layer.next_drawable()`. AppKit's `displayLayer:` and subsequent
window activation callbacks pause the link and synchronously ask GPUI to draw.
That enters the forbidden fallback after the layer has become owned by a Metal
display link. A paused link still owns acquisition. The layer-backed
`render_to_image` method had the same unchecked acquisition path.

The reported `17*.ips` files were not present during this investigation. The only
available current report was a separate Rust entity double-lease abort; it was
not used as evidence for this Metal exception. The exact reason above comes from
the successful standalone reproduction, not an inferred crash-report field.

Apple's contract also explicitly says to consume the supplied drawable:
[Apple rendering-loop reference](https://github.com/apple/game-porting-toolkit/blob/main/game-porting-skills/skills/presenting-metal-drawables/references/render-loop-detail.md).

## Candidate fix in this commit

- `gpui_apple::drawable_source::DrawableSource` models manual versus Metal-link
  acquisition. After binding a Metal link, lack of a supplied drawable returns
  no drawable; it cannot call the manual-acquisition closure. Consuming a drawable
  does not reset ownership. Callback cleanup releases unused supplied drawables.
- The renderer binds ownership before constructing CAMetalDisplayLink. Drawing
  rejects nonpositive/nonfinite sizes; layer-backed capture rejects Metal-link
  acquisition and directs callers to offscreen scene capture instead.
- `MacWindow::draw` preserves a forced-render request if a drawable is unavailable
  or the window is hidden, minimized, occluded, screenless or has invalid size.
  AppKit repaint and activation requests on Metal-link windows are deferred to
  the next supplied-drawable update. The link callback also checks visibility
  and a nil drawable. The CV/ordinary CA fallback remains separate.
- No UI design or visual assets were changed.

**Do not call this fixed in production yet.** The standalone acquisition-state
regression passes, but the full patched renderer and app still need a successful
build and the on-screen acceptance run.
